# 公共 64 位改造开发计划

## 1. 目标、范围与当前状态

目标：消除 OpenNox 引擎对 32 位宿主地址和 ABI 的依赖，以 **Windows amd64 原生客户端与服务器实际运行**验证公共改造，同时保留 Windows/Linux 386 的现有行为与 Nox 1.2b 数据、存档和网络兼容性。

本计划供不同 AI agent 实例跨会话接续执行。计划制定于 2026-09-17，源码调查基线为 `7a975b230b1188a828e7568990adf5f4f3446e0e`（`fork/main`）。该提交是调查起点，不代表已完成本计划要求的基线验收。执行状态与交接记录见 [进度台账](porting-64bit-progress.md)。**当前仅完成计划，尚未实现或验证 64 位支持。**

纳入范围：类型和布局分类、内存映射、分配器与句柄、Go/C 边界、回调、脚本引用、序列化、架构可选构建、Windows x64 验证。

暂不纳入：Darwin 系统后端、ARM64 实机适配、Metal 重写、macOS 打包签名、玩法修改、全面 C 转 Go、无关依赖升级。公共代码不得引入 Windows 专用地址模型；Windows x64 通过不能标记 macOS 或 ARM64 已支持。

## 2. 每个 agent 的执行协议

1. 先读根目录 [AGENTS.md](../AGENTS.md)、[CONTRIBUTING.md](../CONTRIBUTING.md)、[重构指南](refactoring.md)、本计划和进度台账；检查当前分支、HEAD、工作区与已有 worktree。
2. 在台账中领取一个任务 ID，记录基线提交、目标、涉及模块、前置依赖和验收命令。已有任务正在执行时，先核对其状态，不能据时间推断已经完成或放弃。
3. 按一个数据类型及其完整读写/调用链拆分任务；预计无法在一次会话完成时，先拆出有独立验收标准的子任务。不要按大文件随机分配替换工作。
4. 在自己的分支/worktree 工作，保留用户未提交内容。不要让不同实例同时修改同一个工作区；共享头文件、生成器和类型契约的修改串行集成。
5. 每个改动先说明字段含义及兼容策略，再修改生产者、消费者、分配大小、回调和测试。新增功能优先 Go，旧代码重构可使用纯 C。
6. 运行受影响测试和阶段门禁，记录实际命令、环境、退出码及证据。未执行、编译失败、运行失败、外部资源缺失必须分别记录；缺少测试环境不能写为通过。
7. 结束前更新台账、阻塞清单和交接记录，给出精确的下一步。使用英文、祈使句提交标题；重命名、类型调整、逻辑变化按重构指南分开提交。

本计划不授权自动发布、自动创建上游 issue/PR 或部署。准备向上游提交重大设计时，按 CONTRIBUTING 先讨论；可先在本地推进调查和实现。此前两个独立修复的 PR 授权不扩展为本项目的自动提交授权。

## 3. 分支、产物与集成约定

- `fork/main`：保留当前可用版本和本地化能力。
- `port/64bit`：公共改造集成分支，执行 P0 时从选定并记录的 fork 基线建立。
- `port/windows-amd64`：从公共分支派生，仅放 Windows 工具链、平台接口和运行验证所需的专用改动；公共问题回到公共分支修复。
- `task/64bit-<id>-<topic>`：阶段子任务分支，从明确的集成提交派生。未来 `port/macos-arm64` 复用公共分支。
- worktree 建议放在仓库内已忽略的 `build/worktrees/`；创建前检查已有路径。不要为了同步分支重写其他实例正在使用的历史。
- 构建产物与日志分开存到 `build/port64/<commit>/<os>-<arch>/`；避免覆盖当前可运行的 `src/*.exe`。将小型结论、命令和结果写进受版本控制的台账，不能只交接本机日志路径。

集成公共提交必须保持 386 的阶段门禁通过。amd64 在早期允许失败，但要记录第一处阻塞及分类；平台分支的实验不能伪装成公共能力已完成。仅编译成功不能作为运行验收。

## 4. 已确认的源码入口与风险

以下是调查入口，并非完整扫描结果；P0 需要继续追踪所有调用方。

| 入口 | 已确认现象 | 需要回答的问题 |
| --- | --- | --- |
| `src/internal/noxbuild/main.go` | CGO 目标固定 `GOARCH=386`；Windows 交叉编译器固定 i686 | 如何显式选架构、校验编译器并隔离产物？ |
| `src/main.go`、`src/legacy/cnxz/nxz.go` | 要求 Go `int` 为 4 字节；NXZ 将 Go 长度变量地址转成 `*C.int` | 需显式 C 长度变量和范围校验，不能只删除断言 |
| `src/common/memmap/`、`src/legacy/memmap.go` | 原地址映射与宿主指针共同存在 | 哪些访问表达原始偏移，哪些读写真实指针？ |
| `src/common/memmap/nox/blobdata/blob_init.go` | 指针写入位置存在相邻 4 字节槽，例如 7220 与 7224 | 8 字节指针写入会重叠；必须迁移全部别名与访问方 |
| `src/server/object.go`、`src/legacy/defs.h` | Go/C 对象同时包含指针、整数和原偏移注释 | 两侧结构和旧 C 裸偏移如何同步迁移？ |
| `src/server/player.go`、`src/server/save.go` | 存在精确大小与字段偏移断言 | 哪些是外部格式，哪些只是旧运行时 ABI？ |
| `src/legacy/gui*.go`、`src/legacy/audio_ail.go` | GUI、动画、音频结构依赖旧布局 | 消息参数或回调中是否夹带对象指针？ |
| `src/legacy/common/alloc/`、`alloc/handles/` | C 堆分配、大小转换、保护地址区生成伪指针句柄 | 生命周期、长度溢出和 32 位存储槽如何处理？ |
| `src/legacy/common/ccall/`、`src/internal/exportpkg/` | 包含回调包装与代码生成路径 | 函数真实签名是否与包装一致？生成源在哪里？ |
| `src/legacy/cgo_common.go` | 当前关闭多种指针/整数转换警告 | 如何逐步暴露风险并防止新增截断？ |
| `src/legacy/server__script__*`、`src/server/script*`、`src/go.mod` | 存在脚本及外部脚本/EUD 依赖 | 哪些值必须保留 32 位语义，哪些实际代表宿主对象？ |

## 5. 必须先确定的数据契约

P2 按类型记录下表中的分类。**禁止全局替换 `int`、`uint32` 或把全部指针槽扩大到 8 字节。**

| 数据类别 | 目标契约 |
| --- | --- |
| 宿主运行时指针 | 使用准确的指针类型；确需整数地址时用 `uintptr_t` / `uintptr`，不得中途经过 32 位整数 |
| 外部文件、存档、网络和 VM 数值 | 按原协议使用固定宽度与明确字节序；不能用宿主 `sizeof` 决定编码 |
| 原游戏地址与 blob 偏移 | 使用显式逻辑地址/偏移语义，经转换访问；不得直接当成宿主地址 |
| 对象 ID、脚本引用、句柄 | 与指针分离；确认是否需要 32 位 token、映射表及失效检测，不能默认现有编号可代替指针 |
| 运行时共享结构 | Go/C 的大小、对齐、偏移一致；所有字段访问和分配同步更新 |
| 混合布局 | 明确采用原布局代理加宿主映射，或迁出到原生结构加访问接口；按模块决策，不能混合两套不兼容解释 |

决策必须涵盖：原字段含义、读写方、所有权、空值/哨兵、生命周期、数组步长、序列化边界，以及旧裸偏移是否仍可访问。为一个代表性结构和一组相邻 blob 指针槽先做小范围验证，再推广。

特别约束：

- Windows x64 是 LLP64，macOS 等常见 Unix 64 位平台是 LP64；不能用 `long` 作为跨平台指针整数或固定宽度格式类型。保留原游戏 UTF-16/2 字节字符契约，单独审计 `-fshort-wchar` 的系统接口边界。
- `uintptr` 不保持 Go 对象存活，也不允许绕过 CGO 指针规则；C 长期持有的引用必须有明确所有权和释放机制。不要把包含 Go 指针的对象任意复制到 C 堆。
- 不依赖所有分配都低于 4 GiB，不关闭 ASLR，不以强制低地址分配作为最终方案。真实分配测试需覆盖高地址；人为构造的整数地址不得直接解引用。
- 保留外部格式断言。运行时布局改变时，将旧断言替换为有依据的跨架构/Go-C 一致性检查，而非直接删除。
- 不使用 `pack(1)` 掩盖布局变化，不假设 x86 容忍的非对齐访问在其他架构同样安全，不用函数指针强转掩盖签名差异。
- 不关闭全部警告、`checkptr` 或 CGO 检查来宣布成功。现存问题可单独列账，不能把新增问题归为历史遗留。
- [重构指南](refactoring.md)中的“新指针先赋给旧 int”是拆分改动示例；64 位路径不得引入这种截断过渡。用安全的中间表示或保持未就绪路径的架构保护。

## 6. 分阶段执行与验收门禁

依赖主线：`P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7`。P2 的调查可与 P1 交错；P3–P5 可按已确定契约的模块迭代，但不能跳过相应验收。Windows 工具链验证从 P1 开始，不能留到最后才发现架构不匹配。

### P0：基线、工具链清单与阻塞清单

**任务**

- P0.1 记录 HEAD、工作区、Go/GCC 版本、`gcc -dumpmachine`、SDK/依赖来源、DLL 架构与游戏数据位置。先核实本机可用的 x64 工具链，不能仅凭终端名称判断。
- 在记录过的基线上创建或复用 `port/64bit` 及独立 worktree；将本计划与台账带入该分支。后续实例先检查分支是否存在，不能重新创建并覆盖已有进展。
- P0.2 建立独立 386 产物；构建 HD 调试客户端、HD 客户端和服务器，运行完整测试并分类已有失败。保存可重复的启动、进地图、存读档和联机基线步骤。
- P0.3 扫描指针整数转换、Go/C 布局断言、裸偏移、`memcpy`/`fread`/`fwrite` 长度、回调和外部依赖；每项标记数据类别、调用方和风险。搜索命中只是调查线索，不能当成已经确认的缺陷数量。

**交付/门禁**：可重现的 386 构建与运行记录；有测试结果的基线提交；分类阻塞清单。若基线无法进入游戏，先明确环境或原有故障，不得把无法对照的运行失败算作迁移成功。

### P1：可选架构构建与诊断入口

**任务**

- P1.1 为 `noxbuild` 增加显式 `-arch`，保留默认 `386`；显式参数优先，不再静默用固定值覆盖用户目标。按 OS/架构选择或验证 `CC`，不要仅根据 GOOS 判断是否需要不同编译器。
- P1.2 为 Windows amd64 使用同一套 x64 C 工具链、导入库和运行库；隔离 386/amd64 的 PATH、pkg-config 搜索路径和产物。记录 OpenAL 实际导入库名称；不得复用 32 位库的复制方案到不匹配架构。
- P1.3 创建可重复的架构构建与诊断命令，保存 amd64 失败日志。按模块收集此前被抑制的转换/函数签名警告，区分编译阻塞与潜在运行错误。

**交付/门禁**：386 默认行为不变；架构参数和错误编译器能够通过有针对性的验证；x64 产物用 PE 头或 Go build info 确认架构。此阶段不要求完整 amd64 游戏构建成功，不移除其保护检查。

### P2：布局策略与兼容性测试基座

**任务**

- P2.1 按第 5 节分类核心结构和指针槽；记录采用原生结构、代理布局或句柄方案的理由及完整访问边界。无法确定的字段保留为阻塞，不凭命名猜测。
- P2.2 建立 Go/C 大小、对齐、字段偏移的比对；对外部格式保留固定值检查。设计至少一个含指针结构和相邻 blob 槽的验证样例，证明不重叠且两侧解释一致。
- P2.3 准备可提交的合成二进制样本与预期输出，覆盖读写边界、字节序、空引用和长度溢出。已有 Nox 资源和私人存档仅在本地使用，不提交游戏资产。

**交付/门禁**：有证据的布局决策记录、可在相关架构运行的独立测试，以及字段的生产者/消费者清单。不得先全局改布局再补调用方。

### P3：内存映射、分配器、句柄与回调基础

**任务**

- P3.1 迁移 `memmap`/blob 中的宿主指针槽及其所有读写方，处理原地址别名、相邻槽、数组步长和初始化。仅改 `PtrPtr` 不足以修复 C 的直接访问。
- P3.2 审计分配大小、乘法溢出、`size_t` 到 `int` 转换、释放和保护地址区。为需要 token 的对象明确分配、失效、复用和并发策略；不要把现有单调句柄无条件改成可复用句柄。
- P3.3 审计 `ccall`、导出函数和调用者的参数/返回值真实语义，指针和数值分开；修改生成源并重生成。`ccall.go` 的入口是 `legacy/common/ccall/callgen`，不能只手改生成结果。
- P3.4 对新增抽象做高地址传递、空值、边界、反复创建释放、陈旧句柄（若设计支持）、C→Go→C 回调验证。检查高位是否在完整链路保留。

**交付/门禁**：相关基础包在 386/amd64 的测试通过；没有重叠指针写入或新地址截断；生成结果可复现。记录暂未迁移的旧访问路径，不能宣布全局已安全。

### P4：引擎对象与子系统逐项迁移

按以下任务组推进；实际先后由 P0 的依赖图决定。一个任务组通常需要多个小提交，不能把整组当成一次机械替换。

| 任务 | 范围 | 最小验收 |
| --- | --- | --- |
| P4.1 | `Object`、对象类型、链表、玩家、NPC、更新数据及对应 C 定义 | 创建/更新/删除、链表连接、对象引用和 Go/C 布局验证 |
| P4.2 | 文件句柄、内存文件、NXZ 压缩解压、资源加载 | 已知样本解码、往返与边界检查；不能只删除 `cnxz` 的 int 宽度断言 |
| P4.3 | 脚本 VM、脚本对象映射、激活器和第三方脚本/EUD 边界 | 保留 32 位 VM 数值语义；对象引用和代表性事件执行正确 |
| P4.4 | GUI、控件消息、动画、字体、绘制、音频回调 | 含指针的消息往返、资源释放、菜单和音频相关测试 |
| P4.5 | 战斗、AI、物品、法术、地图切换等剩余调用链 | 相关行为测试/可复现场景；完整调用链的裸偏移与步长已审计 |

每组都要检索同一字段的数字偏移、C 头文件、Go 定义、数组复制及序列化入口。无法在全游戏启动前进行场景测试的项目标记“等待 P6”，不可填已通过。

**交付/门禁**：所有客户端与服务器链接路径中的布局冲突、指针截断和不一致回调签名已解决；对应 386 回归通过，amd64 构建可推进。只有当原保护条件已被安全实现与测试替代时，才移除 `main.go` 等全局 32 位保护。

### P5：文件、存档、网络与依赖兼容

**任务**

- P5.1 审计按运行时结构大小读写的文件/存档代码；分离运行时对象与外部表示，保持原字段宽度、字节序、加密/压缩边界和对象标识规则。
- P5.2 检查网络消息编码、对象引用和解码长度。386 与 amd64 对相同输入生成相同的协议字段；时间戳、随机值等差异只能按记录过的语义规范化比较。
- P5.3 对脚本、音频、图形等依赖检查架构假设。依赖修复用可追踪提交或版本，禁止直接编辑 Go 模块缓存并把本机成功当作可复现修复。

**交付/门禁**：格式 golden tests 在两种架构通过；合成样本互读互写；私人存档/原版数据的运行验证纳入 P6。传统 EUD 若依赖原进程裸内存布局，需单独记录兼容边界，不能把静默损坏称作兼容；影响本次目标的未决问题必须列为阻塞。

### P6：Windows x64 端到端验证

**任务**

- P6.1 审计 Windows 句柄、socket、系统回调和 DLL 导入；构建 x64 HD 调试客户端用于诊断，再验证正式 HD、普通客户端与专用服务器产物。
- P6.2 使用明确的 `-data` 路径运行第 8 节矩阵；默认资源和 `-lang zh-CN` 分别测试。保护私人存档，使用可恢复的测试档；不以更改原游戏资源解决移植缺陷。
- P6.3 记录崩溃堆栈、触发步骤、模块、版本与修复后的复验；公共缺陷回流 `port/64bit`，Windows 专用修复保留平台边界。

**交付/门禁**：第 8 节必测项全部有可复核证据。仅看到进程、启动日志、菜单或 PE64 标识，都不足以宣称“Windows x64 跑通”。

### P7：持续验证、文档与交接

**任务**

- P7.1 CI 添加独立的 386/amd64 构建与无需游戏资源的测试，按架构隔离缓存/产物，保留 Linux 386 既有验证。确认 fork 的目标分支会触发检查，不能假设当前工作流覆盖 `port/*`。
- P7.2 公共设计尽早在可用的 LP64 环境做相关类型/边界测试，记录实际平台和结果；尚无环境时明确其未验证，不阻止报告已完成的 Windows 目标，但不能宣称跨平台验收完成。
- P7.3 更新构建说明、已知限制和完整验收记录；按独立问题整理可上游提交的英文提交与说明。CI 验证任务不应意外触发当前 release 工作流的发布步骤。

**完成定义**：公共代码具备 64 位表示与安全边界；386 未引入已知回归；Windows x64 矩阵通过；新检出的截断/布局/兼容性阻塞清零；未测平台与扩展兼容限制被明确记录。不能仅因一个阶段耗时过长而跳过或缩小验收。

## 7. 构建与验证命令约定

以下 Bash 命令从 `src/` 执行。386 使用 MINGW32；amd64 使用 P1 核实过的 x64 环境（如 MINGW64），两者不混用库路径。工具安装包和版本在执行时核实，不在本计划中假定本机已具备 x64 依赖。

当前可用的 386 基线命令：

```bash
go version
gcc -dumpmachine
go env GOOS GOARCH CGO_ENABLED CC
mkdir -p ../build/port64/baseline/windows-386
go run ./internal/noxbuild -o ../build/port64/baseline/windows-386 client-hd-debug client-hd server
GOOS=windows GOARCH=386 CGO_ENABLED=1 \
CGO_CFLAGS_ALLOW='(-fshort-wchar)|(-fno-strict-aliasing)|(-fno-strict-overflow)' \
go test ./...
```

下面是 **P1 需实现的命令契约，当前 `-arch` 尚不存在**。执行时将 `candidate` 换成实际提交标识；先确认 `CC`/库路径匹配架构。

```bash
mkdir -p ../build/port64/candidate/windows-amd64
go run ./internal/noxbuild -arch amd64 -o ../build/port64/candidate/windows-amd64 client-hd-debug client-hd client server
GOOS=windows GOARCH=amd64 CGO_ENABLED=1 \
CGO_CFLAGS_ALLOW='(-fshort-wchar)|(-fno-strict-aliasing)|(-fno-strict-overflow)' \
go test ./...
go version -m ../build/port64/candidate/windows-amd64/opennox-hd-debug.exe
objdump -f ../build/port64/candidate/windows-amd64/opennox-hd-debug.exe
```

运行示例（按本机实际路径设置变量）：

```bash
NOX_DATA='/e/GOG_Galaxy/Games/Nox'
../build/port64/candidate/windows-amd64/opennox-hd-debug.exe -data "$NOX_DATA" -window
../build/port64/candidate/windows-amd64/opennox-hd-debug.exe -data "$NOX_DATA" -lang zh-CN -window
```

测试先运行改动涉及的包；阶段集成运行完整套件并与 P0 对照。当前本地化与字体资源测试包为 `./internal/localization`、`./client/noxrender`。`go test` 不能替代带 `highres`/`server`/`guiapp` 等不同构建标签的实际目标构建。

`noxbuild -safe` 会启用包含 AddressSanitizer 的 C 构建路径；运行时 `-safe` 是另一个入口。不得假设 Windows 工具链支持该构建模式。先验证可用性，再选用 sanitizer、Go 指针检查或调试器；不可因工具不可用省略功能/边界验证。

## 8. “Windows x64 跑通”的验收矩阵

所有项记录提交、架构、构建标签、工具链、数据版本、步骤、预期/实际结果和证据；图形行为需要真实 UI/人工验证，日志不能证明画面正确。测试网络会话使用本地/授权环境。

| 项目 | 必测行为 |
| --- | --- |
| 产物架构 | PE amd64，Go build info 为 windows/amd64；依赖 DLL 为 x64，实际启动的是本次产物 |
| 基础启动 | 默认资源进入菜单；音频、鼠标、键盘、窗口切换正常；退出无异常 |
| 本地化 | `-lang zh-CN` 中文文字和三个字体正常；覆盖资源缺失时按既定规则回退；无参数保留默认行为 |
| 单机 | 战士、法师、召唤师各进入一张代表性地图，覆盖移动、战斗、物品、施法/召唤、脚本事件与切图 |
| 存读档 | 386 保存→amd64 读取，amd64 保存→386 读取；关键角色/物品/任务状态一致；原版 1.2b 代表性存档可读 |
| 客户端/服务器 | x64 客户端连接 386 服务器、386 客户端连接 x64 服务器、x64 双端；完成加入、移动、战斗、切图、离开 |
| 原版协议 | 在可用的合法 Nox 1.2b 环境验证代表性互联；若环境缺失，标记阻塞或未验证，不能仅用 OpenNox 双端代替原版兼容结论 |
| 生命周期 | 同一进程至少连续 10 次进出地图/会话，检查对象、回调和资源释放；代表性游戏会话至少持续 30 分钟，记录异常及内存趋势 |
| 386 回归 | 同提交的 Windows 386 客户端/服务器构建、测试与核心运行流程通过；Linux 386 构建/测试记录可复核 |

基线已有失败必须逐项列出证据和影响。影响上述核心玩法、存档或网络兼容的失败不能作为笼统豁免；若需要调整目标，明确记录用户确认后的范围变更。

## 9. 风险处理与后续平台边界

迁移最大的工作量通常来自共享结构及其所有旧偏移访问，而非编译参数。P0 完成前不给工期承诺；按已迁移的完整链路和通过的门禁衡量进展，不按修改行数或减少警告数衡量。

遇到不明字段、第三方架构限制、无法获取的原版测试环境或不可复现崩溃时，在台账记录最小复现与待决问题，继续不依赖该问题的任务。禁止用空实现、跳过关键测试、禁用玩法或忽略错误来越过门禁。

macOS 后续在公共分支上补 Darwin 内存/网络实现、ARM64 ABI 验证、Clang/SDK 适配及窗口/输入/打包。需要平台特例时隔离在平台文件中；不要将 `windows/amd64` 当作所有 64 位平台的唯一模型。
